# K99 — MSRV bump to Rust 1.95

## Context

flui-v2 is a hard fork of `gpui-ce`. Per `.ai-factory/RESEARCH.md` and `.ai-factory/ROADMAP.md`, the project entered Phase 0-K Kernel Cleanup as of 2026-05-08 — a sequenced set of architectural fixes (K01–K22 + hygiene K90–K99) that repay structural debt in `flui-core` before the Framework tier (Phase II-F, SF##) can be built on top.

K99 is the **first** spec in the critical chain because it unlocks Rust idioms used by all subsequent K-specs:

- AFIT (`async fn` in traits) and RPITIT (`-> impl Trait` in traits) — needed for `Widget::build(&self) -> impl Widget` in K03 and SF01 without `Box<dyn>` allocations on the rebuild hot path.
- Edition-2024 lifetime captures (`-> impl Trait + use<'_>`) — for precise async/iterator return-type lifetimes in K01 (Provider) and K05 (Element ctx-object).
- Async closures stable (1.85+) — for callback APIs used in K07 (token-based borrow) and SF05 (setState).
- `let-chains` (1.88, edition 2024) — collapses nested `if let` patterns in K02 (reconciliation).
- `std::sync::OnceLock` (1.70+, replaces `once_cell::sync::OnceCell`) and `std::sync::LazyLock` (1.80+, replaces `once_cell::sync::Lazy`) — drops the `once_cell` crate dependency in K01. Single-threaded variants: `std::cell::OnceCell` and `std::cell::LazyCell`.
- `unsafe extern "C"` (1.82+) — required syntax in edition 2024 for FFI in `flui-platform`.
- `#[diagnostic::on_unimplemented]` (1.78+) — better trait-bound error messages on Framework-tier traits.

Prior to K99, the workspace declared `rust-version = "1.85"` in `Cargo.toml` but only `flui-platform` propagated it. The other 11 workspace members compiled on whatever stable Rust the runner happened to have, NOT the declared MSRV. CI used `dtolnay/rust-toolchain@stable` everywhere — pulling latest stable, ignoring the workspace declaration. **The MSRV declaration was purely cosmetic.** K99 turns it into a real invariant.

## Goals

1. Bump `[workspace.package].rust-version` to `"1.95"`.
2. Pin developer toolchain via `rust-toolchain.toml` so rustup-based contributors hit the same floor.
3. Propagate `rust-version.workspace = true` to all 11 workspace members that lacked it.
4. Add `msrv = "1.95"` to `clippy.toml` so MSRV-aware lints become active.
5. Convert CI from "MSRV-declarative" to "MSRV-enforced" — existing 5 jobs honor `rust-toolchain.toml` and become the de facto MSRV gate; add a non-blocking `forward-compat` job that explicitly bypasses the pin to detect upcoming Rust changes.
6. Update all MSRV references in documentation (AGENTS.md, DESCRIPTION.md, ARCHITECTURE.md, RESEARCH.md, rules/base.md).
7. Document the three-file synchronization invariant (`Cargo.toml` ↔ `rust-toolchain.toml` ↔ `clippy.toml`) and bump cadence.

## Non-goals

- `cargo update` / Cargo.lock refresh — FREEZE policy adopted; deferred to a separate hygiene PR if needed.
- CI feature-powerset matrix expansion — that is roadmap item R5.
- Migration guide for downstream consumers — N/A (hard fork, pre-1.0, no downstream).
- Repairing `tooling/perf` orphan status (declares `edition.workspace = true` but not in `[workspace] members`) — deferred to K93 (TODO/dead-code triage).
- Pinning `flake.nix` to a specific Rust version — kept on `fenix.latest` deliberately as forward-compat radar for Nix-based contributors.
- Exploring use of new idioms in existing code — that is the work of subsequent K-specs (K01-K05) and SF specs.

## Design

### The three-file synchronization invariant

```
       ┌──────────────────────────────────────────────────────┐
       │  Cargo.toml [workspace.package].rust-version = "1.95"│
       │     ↓ inherited by every workspace member            │
       │     ↓ enforces minimum version at `cargo check`      │
       └──────────────────────┬───────────────────────────────┘
                              ║ MUST agree
       ┌──────────────────────┴───────────────────────────────┐
       │  rust-toolchain.toml  channel = "1.95"               │
       │     ↓ rustup activates this toolchain in repo dir    │
       │     ↓ dtolnay/rust-toolchain@stable respects this    │
       │     ↓ → CI standard jobs run on 1.95                 │
       └──────────────────────┬───────────────────────────────┘
                              ║ MUST agree
       ┌──────────────────────┴───────────────────────────────┐
       │  clippy.toml  msrv = "1.95"                          │
       │     ↓ Clippy's MSRV-aware lints (manual_let_else,    │
       │       redundant_pattern_matching, ...) consider this │
       │       floor when deciding if a modern idiom applies  │
       └──────────────────────────────────────────────────────┘
```

Drift between any two of these is a bug. K-track and any future MSRV bump must touch all three together.

### Per-member inheritance

```

  "crates/flui-core",        ← rust-version.workspace = true (added)
  "crates/flui-platform",    ← rust-version.workspace = true (was already)
  "crates/flui-macros",      ← added
  "crates/flui-widgets",     ← added
  "crates/flui-navigator",   ← added
  "crates/flui-a11y",        ← added
  "crates/flui-theme",       ← added
  "crates/flui-material",    ← added
  "examples/nav_demo",       ← added
  "examples/material_demo",  ← added
  "examples/animation_demo", ← added
  "tooling/lock-checks",     ← added
]
```

`tooling/perf/` is NOT a member. Its `Cargo.toml` declares `edition.workspace = true` and references workspace deps but is not built by `cargo build --workspace`. K93 (dead-code triage) will resolve.

### CI architecture

```
   .github/workflows/ci.yml
   ──────────────────────────
                                rust-toolchain.toml ←─┐
                                       │             │
                                       ↓             │ pinned to 1.95
   ┌─────────────────────────────────────────────┐  │
   │ Standard jobs (BLOCKING):                   │  │
   │ - check         (Linux + macOS)             │──┘
   │ - check-windows (Windows)                   │  → All run on 1.95
   │ - clippy        (Linux + macOS)             │  → DE FACTO MSRV GATE
   │ - test          (Linux + macOS)             │
   │ - format        (Ubuntu)                    │
   └─────────────────────────────────────────────┘

   ┌─────────────────────────────────────────────┐
   │ forward-compat (NON-BLOCKING):              │
   │ - rustup default stable && rustup update    │  → Bypasses toolchain.toml
   │ - cargo check --workspace                   │  → Runs latest stable
   │ - continue-on-error: true                   │  → Detects upcoming breakage
   └─────────────────────────────────────────────┘
```

### flake.nix divergence (intentional)

`flake.nix` continues to use `fenix.packages.${system}.latest.withComponents` — Nix-based contributors get latest stable Rust, NOT the MSRV pin. This is deliberate:

- Nix users complement the CI `forward-compat` job — local development on bleeding edge surfaces issues before the next MSRV bump.
- Reproducibility for Nix users is achieved through `flake.lock`, not toolchain version pinning.
- Pinning fenix to 1.95 would force Nix users to manually update on each MSRV bump, with little benefit (CI standard jobs are the real MSRV gate).

A one-line comment in `rust-toolchain.toml` documents this choice.

## API surface

**Zero source-code API changes.** This is a configuration / metadata change only. No public type, function, trait, or module signature is modified. No new dependencies introduced.

**Indirect API impact:** subsequent K-specs and SF-specs MAY now use Rust 1.85–1.95 idioms previously forbidden. Each downstream spec is responsible for its own API decisions. K99 only opens the door.

## Migration / Compatibility

### Hard-fork posture

Per `.ai-factory/DESCRIPTION.md` and `.ai-factory/RESEARCH.md`, flui-v2 is a hard fork of `gpui-ce` with no upstream-sync commitment. MSRV bumps are unilateral. There are no downstream consumers (pre-1.0, not yet on crates.io).

### Cargo.lock policy: FREEZE

Three policies were considered:

| Policy | Action | Trade-off |
|---|---|---|
| **FREEZE** (chosen) | Keep current `Cargo.lock`, only update if forced by build | Reproducibility wins; orthogonal concerns stay separate |
| REFRESH | `cargo update` after bump | Picks up newer compatible versions; risks surfacing unrelated issues |
| SELECTIVE | `cargo update -p <name>` per case | Effort-heavy, only worth it if specific deps need MSRV alignment |

K99 chose FREEZE. `cargo metadata` confirmed no Cargo.lock changes were forced by the declarative bump alone, so no update was required. Cargo.lock changes are deferred to a separate hygiene PR if a future need arises.

### Bump cadence

Recommendation for future MSRV bumps:

1. Wait for the target Rust release to ship and stabilize in `rustup` (avoid pre-stable channels).
2. Verify all workspace members build clean on the new version (`cargo build --workspace --all-features`).
3. Update **all three** synchronized files atomically in one commit:
   - `Cargo.toml` → `[workspace.package].rust-version`
   - `rust-toolchain.toml` → `channel`
   - `clippy.toml` → `msrv`
4. Update doc references (`AGENTS.md`, `.ai-factory/DESCRIPTION.md`, `.ai-factory/ARCHITECTURE.md`, `.ai-factory/RESEARCH.md`, `.ai-factory/rules/base.md`).
5. Run validation: `cargo build`, `cargo test`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all -- --check`.
6. Capture rationale in a follow-up K## or future spec.

Quarterly cadence is reasonable; aggressive cadence (every release) is unnecessary unless a specific feature is needed.

## Open questions

All resolved at implementation time:

- **Pin exact version vs `stable`?** → pinned exact (`channel = "1.95"`). Reproducibility wins. Bump cadence documented above.
- **Wait for 1.95 release?** → not needed; 1.95.0 was already stable (released 2026-04-14). Active toolchain reported `rustc 1.95.0 (59807616e 2026-04-14)`.
- **Add MSRV check job redundantly?** → no. Once `rust-toolchain.toml` exists, all standard jobs become the MSRV gate. Adding a separate job duplicates work.
- **Pin flake.nix?** → no. Intentional divergence as forward-compat radar for Nix users.
- **Cargo.lock refresh?** → FREEZE. No updates forced; orthogonal concern.
- **Does CI need explicit version override on standard jobs?** → no. `dtolnay/rust-toolchain@stable` defers to `rust-toolchain.toml` when it exists.
